# The AdventureLog API

This page is for people who change the API. People who *use* it start at the interactive docs.

## Where the docs are

| | Address | |
|---|---|---|
| Swagger UI | `/api/docs/` | Browse and try every endpoint. |
| ReDoc | `/api/docs/redoc/` | The same, as one long page. |
| OpenAPI document | `/api/schema/` (`?format=json` for JSON) | OpenAPI 3.0, generated by drf-spectacular. |

On a normal install these open on your AdventureLog domain (`https://example.com/api/docs/`), through the
frontend's proxy. In development, open them on the backend (`http://localhost:8016/api/docs/`): the frontend dev
server does not serve `/static/`, where Swagger UI's files live.

To try requests from Swagger UI, click **Authorize** and paste an API key (Settings → Security), or sign in to
the web app in the same browser and use the session.

The schema is committed as [`openapi/schema.yaml`](openapi/schema.yaml), so every API change shows up in review
as a diff of it. The frontend's TypeScript types are generated from that file.

## Conventions

### Paths

- Everything a client calls is under `/api/`. `/api/auth/browser/v1/…` and `/api/auth/app/v1/…` are
  django-allauth's headless API (sign-in, sign-up, MFA, sessions). The rest is ours.
- Collections of resources are plural kebab-case nouns: `locations`, `lodgings`, `visited-regions`.
  One-per-user resources and namespaces are singular: `account`, `dashboard`, `search`, `calendar`, `backup`.
- Every path segment is kebab-case and ends with a slash. `@action` methods set `url_path` when their name has
  an underscore.
- Records that can exist on their own are top-level, with an optional `collection` field (locations, lodgings,
  transportations, notes, checklists, images, attachments, visits, activities, trails). Records that only exist
  inside a collection are nested under `/api/collections/{collection_id}/`: `days/`, `itinerary-items/`,
  `itinerary/`, `comments/`, `activity/`, and the sharing actions.
- Nested viewsets are registered with a regex prefix on the router
  (`router.register(r'collections/(?P<collection_id>[^/.]+)/days', ...)`) and use
  `adventures.views.mixins.CollectionScopedMixin`. Resources with one object per user or parent use
  `core.routers.SingletonRouter` (`/api/account/`, `/api/integrations/immich/`,
  `/api/collections/{id}/itinerary/`).

Paths and their non-standard names come from `main/api_urls.py`, `adventures/urls.py`, `worldtravel/urls.py`,
`users/urls.py`, `integrations/urls.py` and `billing/urls.py`.

### Methods and status codes

| Method | Use |
|---|---|
| GET | Read. |
| POST | Create (`201` with the resource), or a named state change at `POST …/{verb}/`: `duplicate`, `leave`, `invitation/accept`, `log-visit`, `reorder`, `sync`, `connect`. |
| PATCH | Partial update. PUT only on model viewsets. |
| DELETE | Remove (`204`, no body). Never `POST …/delete/` or `…/revoke/`. Day-plan deletes answer `200` with the new plan, so the planner can redraw. |

| Status | When |
|---|---|
| 400 | The input is not valid. |
| 401 | Not signed in, or a bad API key. |
| 402 | Hosted servers: no subscription (`cloud.middleware.CloudAccessMiddleware`). |
| 403 | You can see the resource but may not do this. |
| 404 | It does not exist **or you cannot see it**. Do not leak existence with a 403. |
| 409 | It conflicts with the current state (already exists, concurrent reorder). |
| 412 | `If-Match` was sent and the record has changed since (see [Writing from an offline client](#writing-from-an-offline-client)). |
| 202 | The work was queued; poll the job in `Location` (see [Background jobs](#background-jobs)). |
| 410 | A job's file expired and was deleted (`job_expired`). |
| 413 | An upload would exceed the owner's media storage. |
| 429 | Rate limited (only when `ENABLE_RATE_LIMITS` is on, except Endurain sign-in, which is always limited). |
| 502 / 503 / 504 | An outside service failed, is not configured, or timed out. |

### Errors

Every error body is the same (`core.exceptions.api_exception_handler`):

```json
{"detail": "name: This field is required.", "code": "validation_error",
 "fields": {"name": ["This field is required."]}}
```

- `detail` is for people, `code` is for programs. Both are always there.
- `fields` appears on validation errors only, with a list of messages per input (`non_field_errors` for the
  request as a whole).
- Some errors add documented context next to them (`limit_bytes` on `413`, `results` on a failed image import,
  `item_count` on `destination_required`).

How to raise one:

- In a view: `raise APIError('Collection not found.', code='not_found', status=404)` (`core.exceptions`), or a
  DRF exception (`NotFound`, `PermissionDenied`, `ValidationError`). Never `return Response({'error': ...})`.
- In a service: raise a subclass of `core.errors.ServiceError` (`DayPlanError`, `QuickAddError`, `BackupError`,
  `IntegrationError`, `MediaQuotaExceeded`, ...). It carries `message`, `code`, `status` and `extra`; services do
  not import DRF.
- An `IntegrityError` becomes `409 conflict` (the day plan names it `order_conflict`).

Codes clients rely on (keep them stable):

| Code | Where |
|---|---|
| `validation_error` | Any 400 with `fields`. |
| `not_authenticated`, `authentication_failed`, `permission_denied`, `not_found`, `method_not_allowed`, `throttled` | DRF's own errors. |
| `conflict` | Already exists, or a database conflict. |
| `precondition_failed` | `412`: the record changed since the `If-Match` version. The body adds `current`, the record as it is now. |
| `media_quota_exceeded` | Uploads, backups and archives over the storage limit. |
| `subscription_required` | 402 on hosted servers. |
| `date_required`, `destination_required`, `stop_required`, `already_planned`, `no_anchor`, `not_day_based`, `day_based`, `order_conflict` | The day plan. |
| `invalid_backup` | A backup or collection archive that cannot be read. |
| `immich.*`, `strava.*`, `endurain.*`, `wanderer.*` | Integrations. |
| `upstream_error`, `upstream_timeout`, `not_configured` | Place lookups, recommendations and image fetching. |
| `location_not_found` | `GET /api/recommendations/` could not find the `location` to search around. |

### Lists

- Lists that can grow without bound (locations, collections, regions) are paged with
  `core.pagination.StandardResultsSetPagination`: `?page=&page_size=` (at most 1000), returning
  `{count, next, previous, results}`.
- Search and pickers take `?limit=&offset=` and return `{count, results, ...}`.
- Lists that belong to one parent (a trip's days, a thread's comments, a location's collections) are plain
  arrays.
- Sorting is `?ordering=field` or `?ordering=-field`, from a list the endpoint documents.

### Query parameters and bodies

Every query parameter and every request body that is not a model goes through a serializer. That one class
validates the input and documents it, so the two cannot drift:

```python
params = validated(LocationListQuerySerializer, request.query_params)   # core.serializers.validated
```

### Authentication and permissions

- `DEFAULT_PERMISSION_CLASSES` is `IsAuthenticated`. A public endpoint says so with `AllowAny` (or a
  read-public permission class), and the schema then marks it as needing no credentials.
- Credentials: an API key (`X-API-Key: al_…` or `Authorization: Api-Key al_…`, `users.authentication`), an app
  session token (`X-Session-Token`, what the mobile app signs in with: `POST /api/auth/app/v1/auth/login`),
  or the session cookie with `X-CSRFToken` on unsafe methods. Requests with a header credential skip CSRF
  (`users.middleware.DisableCSRFForHeaderCredentialsMiddleware`).
- Who may read or change a record is decided in `adventures/access/` and `adventures/permissions.py`.

## Mobile app sign-in

The mobile app signs in as the user, not with a pasted key, and keeps the `X-Session-Token` it is given.

- **Username and password** (and the second factor): allauth's headless *app* client,
  `POST /api/auth/app/v1/auth/login`, then `POST …/auth/2fa/authenticate` with the token from the `401`.
  Signing out is `DELETE /api/auth/app/v1/auth/session`.
- **A provider (OIDC, GitHub…)**: the app never talks to the provider. It opens the system browser at
  `/accounts/mobile/start/?provider=<id>&code_challenge=<S256>&code_challenge_method=S256&state=<random>&redirect_uri=<uri>`
  (`id` is `social_providers[].id` from `GET /api/auth/config/`). The browser signs in the usual way and
  lands on `/accounts/mobile/complete/`, which sends the app to `redirect_uri?code=…&state=…`. The app then
  trades the code at `POST /api/auth/mobile/token/` `{code, code_verifier, redirect_uri}` for
  `meta.session_token`. Codes work once, for a minute; a failed attempt spends the code and a replayed one ends the
  session it made. `redirect_uri` must match `MOBILE_AUTH_REDIRECT_URIS` exactly. Nothing about the provider
  (client, audience, redirect) needs changing on the server.
- Both give the same token. It is the Django session key: it shows under Settings → Security → Sessions, can be
  revoked there, and is extended while in use (`users.authentication.SessionTokenAuthentication`).
- `GET /api/server-info/` lists `capabilities`; the app needs `mobile_auth_v1` to sign in, and uses
  `conditional_writes_v1` and `client_ids_v1` to write safely (below).
- Through the web app's `/api/` proxy, multipart and body-less writes are refused unless they carry an `Origin`
  header equal to the site's own address (SvelteKit's form CSRF check). A native client should send
  `Origin: <the server address it was given>` on writes. JSON writes are not affected.

## Writing from an offline client

A client that keeps a copy of the data and changes it later can end up changing a record that someone else has
since changed, or repeating a create whose answer it never received. Two opt-in features cover this. Neither
changes anything for a client (the web app) that does not use them. The code is `core/sync.py`; the viewsets of
locations, visits, notes and checklists use it.

**Conditional writes** (`conditional_writes_v1`). Reading or writing one of those records returns an `ETag`
(`"<microseconds since 1970 of updated_at>"`). Send it back as `If-Match` on `PATCH`, `PUT` or `DELETE`
(or `*` for "any existing record"):

- the record is unchanged: the request goes through as usual, and the response has the new `ETag`;
- the record has changed: nothing is changed and the answer is `412` with code `precondition_failed`. The body is
  the usual error plus `current` (the record as it is now), and the `ETag` header is its tag.

A request with `If-Match` runs in one transaction that locks the record, so two writers holding the same version
cannot both succeed. Only a record's own `updated_at` is compared: a change to something it merely contains (a
location's visits are their own records) does not change the location's tag.

**Client-chosen ids** (`client_ids_v1`). `POST` accepts an optional `id` (a UUID) for the new record. Repeating
the request is then safe:

| The `id` is... | Answer |
|---|---|
| not used by any record | `201`, the record is created with that id. |
| used by a record the requester can see | `200` with that record as it is stored. The request body is not validated or applied again. |
| used by a record the requester cannot see | `409 conflict`. |
| not a UUID | `400 validation_error`. |

`POST /api/locations/` accepts an optional `visits` list to create a place and its visits in one request.
Nested visits do not need a `location`: the new place is their parent. Their `id` and `location` inputs are
ignored on creation; the response includes their generated ids and parent. Retrying the location's
client-chosen id returns the stored place and visits without creating them again. The standalone
`POST /api/visits/` endpoint still requires `location`.

## Background jobs

Slow work (exports, restores, imports, PDFs) can run in a worker process instead of the request, so it is not cut off by
the gateway timeout and a restart does not lose it. The worker runs inside the app container; the queue is a table in
Postgres ([Procrastinate](https://procrastinate.readthedocs.io)). Nothing else is needed.

### For a client

An endpoint that supports it answers `202 Accepted` with a **job** and a `Location: /api/jobs/{id}/` header:

| Start it with | Result |
|---|---|
| `POST /api/backup/export/` | a zip of the account |
| `POST /api/collections/{id}/archive/` | a zip of one collection (owner) |
| `POST /api/collections/{id}/pdf/` | a Trip Book (trip) or Field Guide (folder) PDF (signed in); the body takes `paper`, `photos` and `journal` |
| `POST /api/backup/import/` with `Prefer: respond-async` | `result.summary`: what was restored |
| `POST /api/collections/import/` with `Prefer: respond-async` | `result.collection_id` and `result.summary` |
| `POST /api/images/import-from-urls/` with `Prefer: respond-async` | `result.created_ids`, `results`, counts |

Without `Prefer: respond-async` the imports, and the `GET` downloads, work as before and answer in the request.

Poll `GET /api/jobs/{id}/` (every second or two) until `status` is `succeeded`, `failed` or `cancelled`. A failed job has
`error` (safe to show) and `error_code`, the same codes the synchronous endpoint would have answered with. A succeeded
export has a `download_url`; the file is deleted after `JOB_RESULT_TTL_HOURS` (24) and then answers `410 job_expired`.
`DELETE /api/jobs/{id}/` cancels a queued job, or removes a finished one with its file; a running job answers `409`.

Imports check the cheap things first (it is a zip, `confirm=yes`, you may change the record) and answer `400` at once.
What only the worker can know (a damaged backup, a full quota) arrives as a failed job, and an account restore changes
nothing unless the whole file loads.

### For a developer

Declare the work once, then start it. The function takes the job row and returns the summary to show:

```python
# adventures/tasks.py
@job_task('account_export')                    # needs_input=True if it reads an upload
def account_export(job):
    with build_archive_file(BackupExporter(job.user)) as archive:
        save_result_file(job, archive, 'backup.zip', 'application/zip')

# in a view
return accepted(start_job(request.user, 'account_export', params={...}, upload=None))
```

- `start_job` creates the `BackgroundJob` row and queues the task **in one transaction**, so a job exists exactly when
  the request's changes do. An uploaded file is saved to storage first (`jobs/<user>/<job>/`), because the worker is
  another process; those paths are never served by `/media/`.
- A `ServiceError` raised by the function (a `BackupError`, for one) fails the job with its message and code. Any other
  exception is logged, shown to the user as a generic failure, and re-raised so the queue records the traceback.
- Small tasks that react to something (geocode a place, e-mail a mention, delete a file) are plain
  `@app.task(retry=RetryStrategy(...))` functions in the app's `tasks.py`; queue them with `task.defer(...)`, in the
  transaction that caused them. Use `queueing_lock` to collapse repeats, and `lock` to keep two from running together.
- Scheduled work is `@app.periodic(cron=...)` on a task in `tasks.py` (UTC); see `jobs/tasks.py`. There is no cron daemon.
- Imports: `jobs` sits beside `worldtravel` in the layers (`.importlinter`); apps above it queue jobs, and `jobs` never
  imports them.
- Tests: tasks are queued for real into the test database. `jobs.testing.run_pending_jobs()` runs what is queued in the
  test's own thread and transaction; `queued_jobs()` asserts what a view queued.
- Development: `manage.py devworker` runs the worker and restarts it on code changes (the dev compose file starts it next
  to `runserver`). `JOBS_RUN_INLINE=true` runs jobs during the request instead, for a process without a worker.

## Adding an endpoint

1. Put the work in a service (see [ARCHITECTURE.md](ARCHITECTURE.md)). The view only translates HTTP.
2. Write serializers for the query parameters, the request body and the response, next to the area's other
   serializers (`adventures/serializers/<area>.py`). Give fields `help_text`.
3. Give the viewset `openapi_tags = ['<a tag from main/openapi.py TAGS>']` and a class docstring that explains
   the resource.
4. Give every method a docstring: the first line is the summary, the rest the description (who may call it,
   what it changes, what it returns). Add `@extend_schema(...)` for what introspection cannot see:

   ```python
   @extend_schema(
       parameters=[SunTimesQuerySerializer],
       responses={200: SunTimesSerializer, 404: OpenApiResponse(description='No times for this date.')},
   )
   @action(detail=True, methods=['get'], url_path='sun-times')
   def sun_times(self, request, pk=None):
       """
       Get sunrise and sunset

       Sunrise and sunset at the place on a date, in its local time. Needs coordinates.
       """
       params = validated(SunTimesQuerySerializer, request.query_params)
       ...
   ```

   The standard 400/401/403/404/429 responses are added automatically by `core.openapi.AutoSchema`; document
   only the others (201, 409, 413, 502...). File downloads use `{(200, 'application/pdf'): OpenApiResponse(response=bytes)}`.
   A `get_queryset` that reads the request starts with `if getattr(self, 'swagger_fake_view', False): return
   Model.objects.none()`.
5. Regenerate the schema and the frontend types, and commit both:

   ```bash
   cd backend/server && python manage.py spectacular --file openapi/schema.yaml --validate --fail-on-warn
   cd frontend && pnpm run api:types
   ```

6. Add a test. `main/tests/test_openapi.py` fails when an operation has no summary or tag, when a route is
   missing from the schema, when `openapi/schema.yaml` is stale, or when a real response does not match the
   schema of the main endpoints.

## TypeScript types

`frontend/src/lib/api/schema.d.ts` is generated with `openapi-typescript` (`pnpm run api:types`) and checked in
CI. Use it through `$lib/api` (`Schemas['Name']`, and aliases such as `Account` and `ApiError`). New code should
take its API types from there. The older hand-written types in `src/lib/types.ts` can be replaced one at a time,
by changing a type to an alias of its schema component and fixing what `pnpm run check` reports.

## Changes in this version

The API was reorganised for consistency. Every change is below; the frontend was updated with it.

### Everywhere

- Errors: `{"error": "..."}`, `{"message", "error": true, "code"}` and bare lists became
  `{"detail", "code", "fields"?}`. Clients that read `.error` should read `.detail`.
- Signed-out requests get `401` everywhere (they got 400, 401 or 403 before). Records you cannot see are `404`.
- Media storage errors are `413` everywhere (attachments and activities answered 400).
- The docs moved from `/docs/` (Swagger 2.0, drf-yasg) to `/api/docs/` (OpenAPI 3, drf-spectacular).
- `?format=json` is still accepted; query strings are validated, so unknown sort fields are a `400`.

### Integrations

Each integration is one resource per user at its own path:

| Before | Now |
|---|---|
| `GET /api/integrations/immich/`, `PUT`/`DELETE /api/integrations/immich/{id}/` (DELETE answered 200) | `GET`/`POST`/`PATCH`/`DELETE /api/integrations/immich/` |

kept their paths, because they are configured outside AdventureLog.

### Fixed along the way

- `PATCH` on the Immich integration crashed.
- Immich image links lacked their trailing slash, so every image request was redirected first.
- A non-number `per_page` for Strava activities was a 500.
- Visited regions and cities: the create views changed the request data, and DELETE took a different id than GET.
- A malformed id on the day plan, sun times or comments was a 500.
- `/invitations/accept-invite/<key>` without the trailing slash skipped AdventureLog's redirect to the sign-up page.
- A signed-out `GET` of the locations list was a 500.

### Known, not changed here

- `ACCOUNT_RATE_LIMITS` is empty unless `ENABLE_RATE_LIMITS` is on, which also turns off allauth's own
  sign-in limits.
- allauth 0.63 publishes no OpenAPI document. The sign-in routes are described by hand in
  [`openapi/allauth.yaml`](openapi/allauth.yaml); allauth 65 and later can serve its own.
